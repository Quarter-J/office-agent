# 长上下文处理

更新日期：2026-09-16。本次增加模型请求预算、滚动摘要和超限恢复，修复了“记忆生成了摘要，但模型仍接收全部原始历史”的问题。

## 请求如何控制长度

所有项目内的 `get_llm()` 调用，包括 Router 的 `bind_tools()` 路径，最终在 [模型接口](../src/api/llm.py) 的请求序列化入口检查预算。实现位于 [context.py](../src/api/context.py)。

```text
可用输入预算 = 配置的上下文窗口 - 输出预留 - 安全余量
```

预算覆盖消息、系统提示、工具定义、工具选择参数、结构化输出定义、工具回执，以及需要回传的 `reasoning_content`。模型输出上限也实际传入请求，不能只在本地计算时预留。

当前采用“UTF-8 字节数 + 消息封装开销”的保守文本估算，不需要下载 tokenizer。它通常比真实 token 数大，因此可能提前裁剪；它不是服务商的精确计数器，也不适用于声称精确计算图片、音频等多模态成本。项目当前的文本路径使用这套策略。

裁剪只作用于模型请求的副本，原始 `AgentState.messages`、生成正文、文件、任务 ID 和 SQLite 动作回执保持完整。

处理顺序：

1. 有滚动摘要时，用摘要和尚未摘要的近期完整轮次构建对话视图；没有摘要时先保留原始历史。
2. 将记忆、检索材料与固定系统指令分开，缩短大段参考文本及工具结果中的正文。RAG 每个片段独立携带来源，避免一段长材料占满整个请求。
3. 如果仍超预算，按完整用户轮次移除最旧历史；工具调用与对应回执一起保留或移除。
4. 继续缩减参考资料和工具结果的文字部分，必要时移除可选记忆背景。
5. 当前用户指令、固定系统约束、工具定义、当前工具调用参数及必要协议字段仍放不下时，停止请求并说明需要分段、知识库检索或调整窗口配置。

JSON 工具结果中的执行状态、是否允许重试、消息 ID、来源和分数保留；正文、摘要等文字可截短，并标记 `context_truncated`。不会把截短后的正文写回发送参数。当前轮次缺少工具调用或对应回执时，拒绝构造不完整请求；历史中的不完整工具轮次整体排除。

聊天界面仍可展示完整历史。模型视图的裁剪不代表删除用户对话记录。

## 滚动摘要如何更新

[记忆管理器](../src/memory/manager.py) 达到阈值后，将“旧摘要 + 尚未摘要的旧消息”合并成一份新摘要。提示词优先保留最新更正、明确约束、未完成事项、目标和执行结果，不能将失败或未知结果写成成功。

- 默认达到 10 条消息触发，保留最近 3 个完整问答轮次；后续请求还会保留尚未覆盖的消息，避免摘要未更新时过早裁剪。
- 新摘要默认最多 800 个字符，替换旧摘要，不再无限追加。超过字符上限的模型文本会裁剪到上限；摘要本身是有损表示，完整执行事实仍以状态和动作记录为准。
- 过长的待摘要历史按 UTF-8 边界分段，逐段合并摘要。所有分段成功后才提交；失败、空输出或超时时，不因本次摘要删除原消息。
- 摘要提交同时移除确切的已摘要前缀。内存回退使用锁，Redis 使用 Lua 原子检查和更新；摘要期间新追加的消息保留，已变化或已过期的快照不能覆盖新记录。
- 消息加入唯一 ID，避免内容相同的多条消息在摘要提交时被当作同一条。
- 修复内存回退的 `ltrim(..., -1)`：超过保留上限时保留最近消息，不再错误地清空列表。

旧配置名 `MEMORY_SHORT_TERM_MAX_TURNS` 和 `MEMORY_SUMMARY_TRIGGER_TURNS` 保持兼容，但单位均为**消息条数**，通常两条消息构成一个问答轮次。短期记忆仍有保留上限；摘要持续失败并超过该上限时，最旧短期消息可能被淘汰。

## 超限与不完整输出

只有服务端明确返回上下文长度超限时，同步 `invoke()` 才以一半输入预算重试一次。两次请求共用原来的模型和任务时间预算。鉴权错误、限流、其他服务错误不会借此自动重试。

重试发生在模型接口内部，不回到工具执行节点。即使消息已经发送，后续总结请求超限也不会因此再次发送。Router 和 Supervisor 遇到无法恢复的长度问题时停止分派，返回 `context_error` 并保留错误说明；业务工具也可通过原有失败结果保留检索材料等已完成数据。

模型以 `finish_reason="length"` 结束时，结果视为不完整，不作为生成成功结果交给发送步骤。

本地已经判断当前指令或执行参数放不下时，不盲目截断，也不先发送超大请求。超长原始用户输入需要用户分段，或先按现有文档入库流程分块后检索；不会自动猜测哪部分可以丢弃。参考材料裁剪只保留部分内容，不能代替要求覆盖全文的逐段审阅。

## 配置

配置已加入 [.env.example](../.env.example)，可按实际模型能力调整：

| 参数 | 默认值 | 含义 |
| --- | ---: | --- |
| `LLM_CONTEXT_WINDOW_TOKENS` | 32768 | 本地使用的模型窗口上限，需与所用模型匹配 |
| `LLM_OUTPUT_TOKENS` | 4096 | 输出预留及实际输出上限 |
| `LLM_CONTEXT_SAFETY_TOKENS` | 1024 | 输入之外的安全余量 |
| `CONTEXT_OBSERVATION_TOKENS` | 2048 | 单份参考材料或工具文字的初始估算预算，受整体预算进一步限制 |
| `CONTEXT_RECENT_TURNS` | 3 | 摘要时期望保留的近期完整轮次 |
| `MEMORY_SHORT_TERM_MAX_TURNS` | 20 | 短期记忆消息条数上限 |
| `MEMORY_SUMMARY_TRIGGER_TURNS` | 10 | 触发摘要的消息条数 |
| `MEMORY_SUMMARY_MAX_CHARS` | 800 | 合并摘要字符上限 |

配置要求窗口大于输出预留与安全余量之和，摘要触发条数不大于短期消息上限。复杂工具定义本身也占窗口，小窗口可能无法支持当前 Router 的全部工具。

关闭记忆时，模型请求仍受总预算保护，但不会生成滚动摘要。直接调用底层模型的异步、批量或流式接口不是本项目应用入口：请求序列化预算仍在对应 Chat Completions 路径生效，本次有界重试与完整输出检查针对项目实际使用的同步 `invoke()`。
